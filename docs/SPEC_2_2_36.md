# vhcctweaks 2.2.36: what it adds

This file is the contract for 2.2.36. The mod and the craftos-agent emulator both implement exactly this. These are general abilities, not features for any one program. Every limit named here is a server config value.

## 1. Linked ender modems

A computer with an ender modem can link to another computer and use that computer's peripherals as if they were wired in.

**Who can link to whom.** Linking needs all of these:
- The two computers have the same owner. The owner is whoever placed the computer, as tracked by `ComputerPlacementTracker`. A pocket computer counts as owned by the player holding it. A pocket computer nobody holds owns nothing, and an unowned computer can't link.
- Both computers are in the same dimension. There is no distance limit.
- Both computers have an ender modem attached. A normal wireless modem doesn't count.

There is no extra opt-in step.

**The Lua API.** These are new methods on the ender modem peripheral:

| Method | Does |
|---|---|
| `link(id)` | Links to computer `id`. Returns `true`, or `false` plus a reason: `"not loaded"`, `"not your computer"`, `"no ender modem"`, `"other dimension"`, `"too many links"` (`maxLinksPerComputer`, default 64). Linking an existing link again returns `true`. |
| `unlink(id)` | Removes the link. Returns `true` if a link existed. |
| `getLinks()` | Returns a list of linked computer ids. |

**How linked peripherals behave.**
- While linked, the ender modem also works as a peripheral hub, like a wired modem. It has `getNamesRemote`, `isPresentRemote`, `getTypeRemote`, `hasTypeRemote`, `getMethodsRemote` and `callRemote`. Its type list includes `peripheral_hub`, so CC's own `peripheral` API lists and wraps remote peripherals with no ROM changes.
- Remote peripherals are named `<id>:<name>`, where `<name>` is the name the remote computer itself uses: a side such as `left`, or a wired name such as `minecraft:chest_3`. A remote computer's own linked peripherals are not passed on; there is no chaining.
- Remote peripherals are attached through `IComputerAccess` the way a wired modem attaches them. So `computer.getAvailablePeripheral` finds them, and every normal method works on them: `pushItems` and `pullItems` between a local and a remote inventory or between two remotes, `list`, `getItemDetail`, monitors, speakers, detectors.

**When the other computer unloads or comes back.**
- If the remote computer unloads or is removed, every one of its peripherals sends `peripheral_detach` with its `<id>:<name>`, and calls on them fail with `"computer <id> is not loaded"`.
- When it loads again, they send `peripheral` and work again.
- Nothing ever loads a chunk.

**Links are not saved.** A program sets its links on every boot.

**Monitor touches.**
- A touch on a remote monitor queues `monitor_touch` with the remote name on the linked computer, as well as the local event on its own computer.
- The touch counts as a fresh interaction on **both** computers.
- `vhcc_touch` with the player's name goes to both, immediately before `monitor_touch`, the same as on 2.2.35.

## 2. Batch inventory methods

These are added to every inventory peripheral through a CC generic source. That covers any block with an item handler, local or remote.

| Method | Does |
|---|---|
| `listDetailed()` | Returns `{ [slot] = detail }` for every non-empty slot. Each detail is exactly what `getItemDetail(slot)` returns, Vault Hunters data included, gathered in one main-thread call. |
| `moveMany(moves)` | `moves` is a list of `{ fromSlot, to, toSlot?, limit? }`. `to` is the name of another inventory, the same as for `pushItems`. Each move behaves exactly like `pushItems(to, fromSlot, limit, toSlot)`. Returns `{ moved = { n1, n2, ... }, done = k }`, where `done` is how many moves were attempted. |

**Limits on `moveMany`.**
- A batch longer than `maxBatchMoves` (default 256) raises an error.
- The batch stops early once its time this tick passes `batchTimeBudgetMicros` (default 2000). It then returns `done < #moves`, and the program calls again with the remaining moves.
- A bad `to` name raises the same error `pushItems` would.

## 3. Inventory change events

| Method | Does |
|---|---|
| `watch()` | Starts sending this computer `inventory_changed` events for this inventory. It is a method on the inventory peripheral, so it works on remote inventories too. Raises an error beyond `maxWatchesPerComputer` (default 64). |
| `unwatch()` | Stops the events. |

**How the event fires.**
- The event is `inventory_changed`, with one argument: the peripheral name as this computer sees it.
- It fires whenever the block's contents change, from a player, a hopper or a computer.
- At most one event goes out per inventory per computer per tick. A double chest's halves are separate blocks, and each half sends its own event.
- Watches end when the computer reboots, or when the peripheral detaches or unloads.

## 4. Spending allowance

| Function | Does |
|---|---|
| `ccvault.requestAllowance(player, maxTokens, minutes)` | Sends that player one chat prompt: "<computer label or "Computer #id"> (owner X) asks to charge you up to N tokens over M minutes [APPROVE]". Returns a request id. When the player answers or the request expires (`nonceExpirySeconds`), the computer gets `ccvault_allowance` with `(requestId, playerName, approved)`. |
| `ccvault.getAllowance(player)` | Returns `remaining, secondsLeft`, or `nil` if there is none. |
| `ccvault.endAllowance(player)` | Ends it. |

**How it works.**
- While the allowance lasts, `ccvault.transfer` from that player to this computer's host needs no fresh touch, up to `remaining` in total. It still needs the player online.
- Each charge lowers `remaining` and is recorded in the ledger as usual.
- It ends on disconnect, on expiry, when used up, or when the player runs `/ccvault revoke`.
- `maxAllowanceMinutes` defaults to 240.

## 5. Smaller changes

- **The host pays a player with no touch.** `ccvault.transfer` from the host to `player:Name` no longer needs that player to have touched the computer recently. They must still be online and approved here. This restores the undone 2.2.36 patch.
- **Longer touch window.** The range of `interactionStaleSeconds` rises to 5–3600. The default stays 30.

## New config values (server)

| Key | Default |
|---|---|
| `links.maxLinksPerComputer` | 64 |
| `inventory.maxBatchMoves` | 256 |
| `inventory.batchTimeBudgetMicros` | 2000 |
| `inventory.maxWatchesPerComputer` | 64 |
| `ccvault.maxAllowanceMinutes` | 240 |
